# daily-summary 성능 최적화 변경 이력

`daily-summary` 리포트 생성 시간을 8분대 → 3분대(Claude Desktop 채팅 기준)로 줄이기 위한
작업 기록. 새로운 최적화를 적용할 때마다 이 파일에 **날짜 + 무엇을 + 왜 + 검증 방법**을
추가한다 — 나중에 회귀가 생기면 어떤 변경이 원인인지 추적하기 위함.

### 6. `chart.umd.min.js`(208KB) 인라인 방식 변경 — 가장 유력한 숨은 병목
- **무엇**: 기존에는 매 리포트마다 모델이 이 파일을 Read해서 그 내용 전체(약 5만 토큰)를
  자기 응답/tool call 인자에 그대로 옮겨 적어야 했다. 이제:
  - 로컬 파일 저장본은 `chart.umd.min.js`를 저장 폴더에 **파일 그대로 한 번만 복사**해두고
    `<script src="chart.umd.min.js">`(상대 경로)로 참조 — 모델이 바이트를 다시 타이핑하지
    않는다.
  - Artifact처럼 CSP로 상대 경로 로드가 막힌 호스트에서만, 그리고 텍스트 재생성이 아닌
    도구(파일 복사/치환)가 없을 때만 최후 수단으로 기존 인라인 방식을 쓴다.
  - Artifact도 `show_widget`도 없는 호스트(Claude Desktop 채팅 자체)는 인라인이 필요한
    "채팅 내부 표시" 사본 자체를 만들지 않는다 — 저장 파일 하나면 충분.
- **왜**: 208KB ≈ 5만 토큰을 매 리포트마다 출력 토큰으로 새로 생성하는 것은 (Claude Desktop
  채팅 기준) 전체 소요 시간의 상당 부분을 차지할 것으로 추정됨 — 아직 실측 완료 전이지만,
  가장 유력한 단일 병목으로 지목되어 우선 수정함.
- **✅ 상대 경로 로딩 자체의 안전성은 조사로 확인함(2026-08-09)**: classic `<script src="...">`
  (Chart.js UMD 빌드가 정확히 이 방식 — `type="module"`이 아님)는 `file://`로 연 로컬 HTML에서도
  CORS 없이 정상 동작한다 — CORS null-origin 차단은 ES 모듈/`fetch`/`XHR`에만 적용되고
  classic script 태그의 로컬 상대경로 로딩은 브라우저가 오래전부터 지원하는 표준 동작이다.
  따라서 이 부분은 추측이 아니라 근거 있는 변경이다.
- **✅ "전용 파일 복사 도구가 없으면 무효화된다"는 우려도 설계로 해소함(2026-08-09)**: SKILL.md를
  "이미 있으면 건너뛴다 → 없을 때만, 전용 복사 도구가 있으면 그걸로, 없으면 일반 파일 쓰기
  도구로라도 1회 생성한다"로 재작성했다. 즉 Desktop이 전용 "파일 복사" 도구가 없고 일반
  "파일 쓰기"(내용을 문자열로 받는) 도구만 지원해도, 208KB 비용은 **해당 출력 폴더 생애 첫
  리포트 1회에만** 발생하고 이후 모든 리포트는 존재 확인만 하고 건너뛴다 — 상각(amortize)되어
  장기적으로는 도구 종류와 무관하게 효과가 남는다.
- **⚠️ 그래도 Desktop에서 직접 실행해야만 알 수 있는 것(Claude Code에서는 검증 불가)**:
  (1) 저장된 HTML을 실제로 열었을 때 차트가 정상 렌더링되는지, (2) 실제 리포트 생성 총
  소요 시간이 목표(3분) 안에 들어오는지 — 특히 "생애 첫 리포트"(자산 파일이 아직 없어 1회
  비용을 치르는 경우)와 "두 번째 이후 리포트"(자산 재사용, 빠를 것으로 예상)를 각각 재서
  비교하면 이 최적화의 실제 기여도를 분리해서 확인할 수 있다. Claude Code 세션은 Desktop
  앱을 구동하거나 그 안에서 시간을 잴 방법이 없어, 이 두 가지는 실제 Desktop 사용자가
  확인해줘야 한다.
- **영향받은 파일**: `SKILL.md` (6/7단계, 보고서 골격의 `<head>` 부분).

### 7. `chart.umd.min.js` 상대 경로 참조 방식 되돌림 — 실사용 실패로 인라인 복귀

- **무엇**: 위 6번에서 도입한 "저장 폴더에 `chart.umd.min.js`를 1회 복사해두고
  `<script src="chart.umd.min.js">`(상대 경로)로 참조" 방식을 완전히 되돌린다. 다시 매
  리포트마다 파일을 Read해서 그 전체 내용을 `{CHART_JS_INLINE}` 자리에 그대로 붙여넣어
  `<script>...</script>` 태그 안에 인라인하는 방식으로 복귀했다 — 호스트에 따라 나누는
  조건부 분기 자체를 제거함.
- **왜**: 2026-08-09 sibling 스킬 `creative-detailed` 실사용 중 실패를 확인함 — 리포트가
  샌드박스 출력 디렉터리(`/mnt/user-data/outputs/`)에 저장됐고, 그 환경의 미리보기가 HTML과
  `chart.umd.min.js`를 서로 별개의 다운로드 가능한 파일 아티팩트 2개로 표시했다. 상대 경로
  `<script src>`가 그 형제 `.js` 파일을 실제로 로드하지 못해 **모든 차트가 깨져(빈 캔버스)
  렌더링**됐다. 위 6번에서 세운 근거("`file://`로 연 로컬 HTML에서 classic `<script src>`는
  CORS 없이 정상 동작한다")는 일반 브라우저로 파일을 직접 여는 경우엔 맞지만, 이 샌드박스
  미리보기 메커니즘에는 적용되지 않는다는 것이 실증됨 — 형제 상대경로 파일을 같은 방식으로
  서빙/해석하지 않는 것으로 보임. 토큰 절약(리포트당 약 5만 토큰)보다 **차트가 실제로
  렌더링되는 것**이 우선이므로, 깨진 리포트가 느린 리포트보다 훨씬 나쁘다는 판단 하에 인라인을
  다시 기본값이자 유일한 경로로 되돌림.
- **비용은 그대로 감수함**: 리포트 1건당 약 5만 토큰(208KB) 인라인 비용은 당분간 그대로
  받아들인다. 아직 구현하지 않은 향후 개선 후보: (1) 호스트가 상대 경로 로딩/파일 복사를
  실제로 지원하는지 사전에 감지하는 방법(호스트 능력 감지), (2) Chart.js보다 훨씬 작은 대체
  차팅 라이브러리로 교체. 둘 다 아직 구현/도입되지 않았다.
- **영향받은 파일**: `SKILL.md` (6/7단계, 보고서 골격의 `<head>` 부분 및 CDN 경고 콜아웃).

### 1. § 실행 방식 절대 지침의 "중간 파일 생성 금지"를 조합 단계까지 명시적으로 확장

- **무엇**: 기존에 "`.py`/`.js`/`.ipynb` 스크립트 파일 생성 금지"만 있던 문구를, "Write/파일
  생성 도구로 만드는 파일은 오직 최종 보고서 HTML 하나뿐 — 예외 없음. 이 금지는 데이터 집계
  단계뿐 아니라 **섹션 HTML을 조합하는 단계에도 동일하게 적용**된다"로 강화하고, 구체적 금지
  예시(`section2.html`, `section4_rows.json`, 임시 스테이징 `final_report.html`)를 추가했다.
  각 섹션 HTML은 그 섹션을 만드는 같은 턴에서 바로 최종 문서 조합에 이어 쓰고, Write는 최종
  저장 시점에 딱 한 번만 실행한다는 문장도 추가했다.
- **왜**: `daily-summary`는 이미 "MCP 응답을 스크래치패드에 썼다가 다시 읽지 않는다"는 지침이
  있었지만, "섹션 HTML 조합" 단계까지 명시적으로 다루지는 않았다 — `daily-detailed`에서 실제로
  이 사각지대(집계 금지는 있는데 조합 금지가 없다고 읽혀서 섹션별 조각 파일을 만들다가 툴호출
  예산이 바닥나 사용자에게 결과를 못 보여준 사고)가 확인됐고, `daily-summary`도 동일한 문구
  구조(집계만 언급)를 갖고 있어 같은 사각지대에 노출돼 있다고 판단해 선제적으로 강화했다.
  `daily-summary`는 이 스킬 자체에서 이 실패가 실측된 적은 아직 없다 — `daily-detailed`의
  사고를 근거로 예방적으로 적용한 것이다.
- **검증 방법**: 다음 `daily-summary` 실행에서 (a) 실행 중 `section*.json`/`section*.html` 등
  최종 파일 외의 Write 호출이 없는지, (b) 각 섹션 HTML이 만들어지는 즉시 조합에 바로 쓰이는지
  확인한다.
- **영향받은 파일**: `SKILL.md`(§ 실행 방식 절대 지침).

### 2. 스켈레톤 선(先) 게시를 "권장 안내문"에서 번호 붙은 필수 체크포인트로 승격

- **무엇**: 기존에 § 실행 방식 절대 지침 아래 별도 안내문으로만 있던 "⏱ 긴 대기 없이 스켈레톤을
  먼저 보여준다" 문구를 삭제하고, § 실행 순서의 **3단계**(2단계 target/achievement 호출 직후,
  나머지 데이터 호출 이전)에 "⏱ 필수 체크포인트"로 번호 붙여 다시 넣었다. 뒤따르는 단계 번호를
  전부 4~9로 다시 매겼고, 그 번호를 참조하던 다른 위치(§ 실행 순서 내 "아래 3/4단계에서" 등,
  § 병렬 호출 지침의 "2단계 먼저, 4단계 나중" 서술, § 완료 메시지 형식의 "8단계에서 저장한",
  보고서 골격 절의 "위 7단계 참고")도 전부 새 번호로 맞춰 갱신했다. 4단계(나머지 도구 호출)에는
  "섹션 데이터가 준비되는 대로 즉시 골격의 해당 placeholder를 교체·재게시한다"는 문장도
  추가했다.
- **왜**: `daily-summary`는 이 최적화의 원조라 스켈레톤 선게시 개념 자체는 이미 있었지만, 번호
  붙은 § 실행 순서 목록에는 포함되지 않고 별도 안내문으로만 존재했다 — `daily-detailed`가 이
  안내문을 그대로 가져다 썼다가 실제 실행에서 완전히 생략된 채 전체 보고서를 다 만든 뒤 한
  번에 저장/게시하려다 툴호출 예산이 바닥나 사용자에게 아무 결과도 못 보여준 사고를 겪었다.
  "권장" 수준의 별도 안내문은 예산이 부족한 실행에서 모델이 가장 먼저 건너뛰는 대상이 된다는
  것이 확인됐으므로, `daily-summary` 쪽도 동일한 구조적 약점을 갖고 있다고 판단해 선제적으로
  번호 붙은 필수 단계로 승격했다.
- **검증 방법**: 다음 `daily-summary` 실행에서 (a) target/achievement 응답 수신 직후 Artifact
  게시가 실제로 한 번 일어나는지, (b) 이후 섹션 완성 때마다 재게시가 일어나는지 확인한다.
- **영향받은 파일**: `SKILL.md`(§ 실행 방식 절대 지침, § 실행 순서 3~9단계, § 병렬 호출 지침,
  § 완료 메시지 형식, 보고서 골격 절의 단계 참조 전부).

### 3·4. `group_by`가 `campaign`/`ad`/`ad-set`인 섹션 대상 asset 스크립트 도입 — 적용 대상 없음(스킵)

`daily-detailed`의 section-4/5에 적용한 `assets/dxd_table_rows.py`(D-1 vs D-0 조인·파생지표·
변화율·화살표·색상·정렬·`<tr>` HTML 생성을 asset 스크립트로 이전)와, `group_by`가
`campaign`/`ad`일 때 media 생략 여부를 재검토하는 항목은 **`daily-summary`에는 적용 대상이
없다.**

- **확인 방법**: `daily-summary`의 5개 섹션 파일(section-1~5)에서 실제로 쓰는 `group_by` 값을
  전부 grep으로 확인했다 — `"media"` 하나뿐이다. `get_target_progress_v2`(section-1)는
  `group_by` 파라미터 자체가 없다. 캠페인/광고그룹/광고 단위로 내려가는 섹션이 처음부터 없다.
- **왜 없나**: `daily-summary`는 배경 설명대로 `daily-detailed`보다 더 간결한 "Executive"
  보고서로 설계되어 있다 — section-5(매체별 성과, D-1 vs D-0)도 Naver Ads/Google Ads/Meta
  Ads/Organic/Others **5개 행 고정** 표이지 캠페인/광고 단위 표가 아니다. 조인+파생지표+
  변화율+화살표+색상 로직 자체는 section-5에도 있지만(D-1/D-0 비교), 대상 차원이 5개 고정
  매체라 행 수가 가변적이지 않고 검색/페이지네이션도 없어(SKILL.md § 공통 표기·렌더링 규칙에
  명시) `daily-detailed`의 캠페인/광고(수십~수백 행, 검색+페이지네이션 필요) 문제와 규모가
  다르다 — asset 스크립트로 옮길 만한 반복·오류 위험이 크지 않다고 판단해 새 스크립트를
  만들지 않았다.
- **결론**: 새 asset 스크립트를 추가하지 않았고, `media` 생략/분리 호출 판단도 재검토할
  대상이 없었다(이미 모든 섹션이 `group_by:"media"` 저카디널리티 단일 호출로 통합된 상태).

## 아직 적용 안 한 후보 (추가 조사/논의 필요)

- `get_target_progress_v2` 3회(media=google/meta/naver) 호출을 1회로 합치는 것 — 현재 도구
  스키마가 `media`를 필수 enum으로 요구해 `media` 생략이 불가능함. 백엔드 스키마 변경이
  필요하며, 매체별로 메시지 포맷이 달라 로직이 복잡해질 수 있어 별도 검토 필요.
- 스킬을 자연어 지시 대신 스크립트(코드 실행)로 전환하는 방식 — Claude Code 문서에서
  권장하는 일반적 기법이나, Claude Desktop이 코드 실행/파일 복사 도구를 지원하는지 확인
  안 됨. 지원 확인되면 MCP 호출 결과 가공 + HTML 템플릿 조립을 스크립트로 옮겨 모델이
  대용량 텍스트를 직접 생성하는 지점을 추가로 줄일 수 있음.
